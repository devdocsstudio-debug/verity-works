better-sqlite3: Common Patterns Guide

A practical companion to the official API reference — the five patterns that come up in almost every real project, with runnable examples.

Sample scope note: this is an independent documentation sample published by DevDocs Studio, the technical-writing service from Verity Works, to show how we work. It is not an official better-sqlite3 document and was not commissioned by its maintainers. It documents the real, public better-sqlite3 npm package at version 13.0.3 by reading its source directly. Every code example and every stated behavior on this page was executed against that installed version before publication — none of it is assumed or guessed. The verification script is sample-better-sqlite3-claims-verify.js.

1. Open a database and set the journal mode

const Database = require('better-sqlite3');
const db = new Database('app.db');

// write-ahead logging: better concurrent read/write behavior than the default
db.pragma('journal_mode = WAL');

db.pragma() both executes a SQLite PRAGMA and returns its result as an array of rows — here, [{ journal_mode: 'wal' }]. Most projects should set WAL mode once, right after opening, unless the database lives on a filesystem that doesn't support it well (some network drives).

2. Prepared statements: run, get, all

better-sqlite3 is synchronous — no callbacks, no promises, no await. A prepared statement is reused across calls instead of re-parsed each time:

const insert = db.prepare('INSERT INTO users (name, balance) VALUES (?, ?)');
const info = insert.run('Ada', 100);
// info -> { changes: 1, lastInsertRowid: 1 }

const getOne = db.prepare('SELECT * FROM users WHERE id = ?');
getOne.get(1);
// -> { id: 1, name: 'Ada', balance: 100 }  (undefined if no row matches)

const all = db.prepare('SELECT * FROM users ORDER BY id').all();
// -> [ { id: 1, name: 'Ada', balance: 100 }, { id: 2, name: 'Grace', balance: 50 } ]

Use .run() for statements that don't return rows (INSERT/UPDATE/DELETE), .get() for exactly one row or undefined, and .all() to materialize every matching row into memory at once.

When a result set could be large, prefer .iterate() over .all() — it yields rows one at a time instead of allocating the whole array:

for (const row of db.prepare('SELECT * FROM users').iterate()) {
  // row is produced lazily
}

3. Transactions are plain functions

db.transaction() wraps a normal JS function; calling the wrapped function runs it inside BEGIN/COMMIT, with automatic ROLLBACK if it throws:

const transfer = db.transaction((fromId, toId, amount) => {
  db.prepare('UPDATE users SET balance = balance - ? WHERE id = ?').run(amount, fromId);
  db.prepare('UPDATE users SET balance = balance + ? WHERE id = ?').run(amount, toId);
});

transfer(1, 2, 25); // one atomic unit; throws roll back both statements together

A frequent misreading of this API: the transaction only rolls back on a thrown JS error. An UPDATE ... WHERE id = ? that matches zero rows does not throw — it just reports changes: 0 — so a transfer to a nonexistent account id still commits the debit half. If "the recipient must exist" is a real invariant, check for it (e.g. inspect changes, or verify the row first) and throw inside the transaction function yourself; the library won't infer that intent for you.

4. User-defined SQL functions

Custom logic can be registered and called directly from SQL:

db.function('SHOUT', (text) => String(text).toUpperCase());

db.prepare('SELECT SHOUT(name) AS shouted FROM users WHERE id = 1').get();
// -> { shouted: 'ADA' }

Useful for small, pure transforms (normalizing text, hashing, formatting) that are awkward to express in SQL but don't justify pulling rows into JS first.

5. Backing up a live database

await db.backup('app-backup.db');
// the live database stays open and usable throughout; the backup is a consistent point-in-time copy

.backup() returns a Promise and uses SQLite's own online backup API, so it's safe to run against a database that's still being written to — unlike just copying the .db file, which can capture a half-written page.

Why a guide like this, separate from the reference docs

The official README documents every method signature; it doesn't tell you that a transaction won't roll back on a logically-wrong but non-throwing update, or when to reach for .iterate() instead of .all(). That gap — between "what each function returns" and "what actually trips people up the first time they use it" — is the gap this kind of documentation is written to close.

Every behavior above was confirmed by running it against better-sqlite3@13.0.3 on Node v24.21.0 in October 2026. Where a result looks surprising, it is the real observed output, not a simplification.
