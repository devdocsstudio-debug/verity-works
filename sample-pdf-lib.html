pdf-lib: Quick Reference for Creating and Modifying PDFs in Node.js

A task-oriented reference for the five operations every pdf-lib project eventually needs — not a method-by-method dump of the API surface.

Sample scope note: this is a portfolio writing sample for the freelance API/developer-documentation candidate, not an official or commissioned document. It documents the real, public pdf-lib npm package at version 1.17.1 by reading its source and type definitions directly. Every code example and every stated behavior below was executed against that installed version before publication — the verification script is sample-pdf-lib-claims-verify.js.

Create a new PDF and draw text on it

const { PDFDocument, StandardFonts, rgb } = require('pdf-lib');

const doc = await PDFDocument.create();
const font = await doc.embedFont(StandardFonts.Helvetica);
// [width, height] in points; omit the array and you get A4, not US Letter
const page = doc.addPage([400, 200]);

page.drawText('Hello, pdf-lib', { x: 50, y: 120, size: 24, font, color: rgb(0, 0, 0) });

const bytes = await doc.save(); // Uint8Array — write it to disk, a response body, or an S3 upload

Three things that trip people up on the first pass.

drawText's y is measured from the bottom of the page, not the top — so y: 120 on a 200pt-tall page is near the middle, not near the bottom.

addPage() with no size argument gives you A4 (595.28 × 841.89 points), not US Letter. If you want Letter, pass it explicitly — PageSizes is exported alongside PDFDocument, so doc.addPage(PageSizes.Letter), or the literal [612, 792].

And the font option is optional, which is the trap — not required. Omit it and pdf-lib quietly embeds Helvetica for you rather than raising an error, so a document whose font never loaded looks like a document that chose Helvetica. page.setFont(font) sets a page-wide default for every subsequent drawText on that page, which is the cleaner way to avoid threading font through every call:

const times = await doc.embedFont(StandardFonts.TimesRoman);
page.setFont(times);
page.drawText('uses the page default', { x: 50, y: 80, size: 14 }); // no font option needed

Load an existing PDF and add a page

const existingBytes = fs.readFileSync('input.pdf');
const doc = await PDFDocument.load(existingBytes);

const page = doc.addPage(); // appended after the existing pages
page.drawText('Appended page', { x: 50, y: page.getHeight() - 50, size: 18 });

fs.writeFileSync('output.pdf', await doc.save());

PDFDocument.load() parses the whole file into an in-memory document object — there's no streaming/partial-load mode. For very large PDFs (hundreds of MB) this matters for memory use; for typical generated reports and forms it's a non-issue.

Merge pages from one PDF into another

const target = await PDFDocument.create();
const [copiedPage] = await target.copyPages(sourceDoc, [0]); // indices of pages to copy, 0-based
target.addPage(copiedPage);

copyPages is called on the destination document, with the source document and an array of page indices as arguments — the direction of the call is the opposite of what most people guess on the first try (target.copyPages(source, ...), not source.copyPages(target, ...)). The returned pages aren't attached to the target automatically; each one still needs an explicit addPage().

Getting and checking page count/size

doc.getPageCount();         // number of pages currently in the document
doc.getPage(0).getSize();   // { width, height } in points for a specific page

Useful for defensive code before an append/merge operation (e.g. "has this PDF already got a cover page?") without re-parsing the file a second time.

Fill in a form field (when the source PDF has one)

const form = doc.getForm();
form.getTextField('applicant_name').setText('Ada Lovelace');
form.flatten(); // optional: bakes the filled values into the page content and removes the editable field

getForm() does not throw when the PDF has no form — that is the trap worth knowing. On a form-less document it returns an empty PDFForm (getFields().length === 0) and adds an AcroForm to the document, so a pipeline that calls getForm() defensively on every file quietly changes files that never had a form. The call that actually throws is the field lookup:

form.getTextField('applicant_name');
// throws Error: PDFDocument has no form field with the name "applicant_name"

So check form.getFields().length (or wrap the getTextField call) rather than relying on getForm() to tell you whether a PDF is fillable.

Why this is a reference, not a tutorial

Each section above answers one question a working developer actually has mid-task ("how do I add a page to a PDF I already have") rather than walking through pdf-lib feature-by-feature from the top. That's the shape most API documentation gaps take in practice: the official docs cover what exists, but not which combination of calls gets a specific real job done.

Every behavior above was confirmed by running it against pdf-lib@1.17.1 on Node v24.21.0 in October 2026. Four of the statements on this page read differently before that run: the default page size, whether the font option is required, whether a page-wide default font exists, and what getForm() does to a PDF with no form. Each is now what the library actually does rather than what the API surface suggests it should — which is the only reason to run the examples instead of describing them.
