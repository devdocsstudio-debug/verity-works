A Playwright Test Suite: UI and API, 48 Tests

A complete, runnable suite against a public demo app — Page Object Model, custom fixtures, role-based locators, desktop and mobile viewports, and coverage shaped around defects rather than features.

Sample scope note: this is an independent portfolio sample published by DevDocs Studio, the technical service from Verity Works, to show how we work. It is not client work and was not commissioned. It runs against demo.playwright.dev/todomvc, the Playwright team's own public demo application, and jsonplaceholder.typicode.com, a public API published for testing. robots.txt was checked for both before a line was written. Last verified run: 48/48 passing across two browser projects.

A Page Object that exposes intent, not selectors

No spec in this suite contains a locator. The page object offers verbs; when the markup changes, one file changes. A suite whose specs are full of CSS selectors is a suite that gets abandoned at the first redesign.

Locators are role- and label-based rather than CSS. These break when the accessible structure genuinely changes — usually a real defect — whereas CSS locators break when somebody renames a class, which is not.

class TodoPage {
  constructor(page) {
    this.page = page;
    this.newTodoInput = page.getByPlaceholder('What needs to be done?');
    this.todoItems = page.getByTestId('todo-item');
    this.counter = page.getByTestId('todo-count');
  }

  async add(title) {
    await this.newTodoInput.fill(title);
    await this.newTodoInput.press('Enter');
  }

  async remove(title) {
    const row = this.item(title);
    await row.hover();                       // the delete control only appears on hover
    await row.getByRole('button', { name: 'Delete' }).click();
  }
}

Fixtures instead of beforeEach

A test that opens async ({ seededPage }) declares its dependency in its signature rather than in a block fifty lines above, and the fixture tears itself down.

const test = base.test.extend({
  // A TodoPage already navigated and ready.
  todoPage: async ({ page }, use) => {
    const todoPage = new TodoPage(page);
    await todoPage.goto();
    await use(todoPage);
  },

  // Pre-seeded with three items, for tests about filtering and counting.
  seededPage: async ({ page }, use) => {
    const todoPage = new TodoPage(page);
    await todoPage.goto();
    await todoPage.addMany(['write the guide', 'run the examples', 'ship it']);
    await use(todoPage);
  },
});

Coverage shaped like a defect list

The happy path is covered. The tests worth reading are the others — the ones a “write some Playwright tests” engagement usually omits.

// NEGATIVE: the single most common real defect in this widget.
test('an empty submission is rejected rather than creating a blank row', async ({ todoPage }) => {
  await todoPage.newTodoInput.press('Enter');
  await expect(todoPage.todoItems).toHaveCount(0);
});

// EDGE: text that would break an implementation interpolating into HTML.
// If this ever renders as markup rather than text, that is an XSS, not a cosmetic bug.
test('markup in a title is rendered as text, not as HTML', async ({ todoPage }) => {
  const nasty = '<img src=x onerror="document.title=\'pwned\'"> & "quoted"';
  await todoPage.add(nasty);

  expect(await todoPage.titles()).toEqual([nasty]);
  await expect(todoPage.page).not.toHaveTitle('pwned');
});

// The defect manual testers miss, because they rarely refresh.
test('todos and their completed state survive a reload', async ({ seededPage, page }) => {
  await seededPage.complete('ship it');
  await page.reload();
  await expect(seededPage.checkbox('ship it')).toBeChecked();
  expect(await seededPage.remaining()).toBe(2);
});

API tests that would fail if the API broke

These assert the contract — keys and types — rather than the copy. A test that pins the title text fails on a content change and tells you nothing about the API.

test('query filtering actually filters, rather than ignoring the parameter', async ({ request }) => {
  const res = await request.get(`${BASE}/posts`, { params: { userId: 1 } });
  const list = await res.json();

  expect(list.length).toBeGreaterThan(0);
  // The negative half is the one that matters: an API ignoring the filter still
  // returns a non-empty list and would pass a length-only check.
  expect(list.every((p) => p.userId === 1)).toBe(true);
});

Ids are also asserted unique, which a count never catches.

One assertion deliberately not written

JSONPlaceholder is a fake backend: writes return a convincing 201 and persist nothing. The POST test asserts the echo and the assigned id, and does not assert that a follow-up GET returns the record.

Writing that assertion would produce a test that passes against a mock while proving nothing — worse than no test, because it reports coverage that does not exist. The reasoning sits in a comment at the test, not in a changelog nobody reads.

Configuration, with the reasons written down

forbidOnly: CI,          // a committed .only is how a suite silently stops
                         // covering anything while still reporting green
retries: CI ? 2 : 0,     // retrying locally hides flake from the person who
                         // can still fix it
trace: 'retain-on-failure',
screenshot: 'only-on-failure',
video: 'retain-on-failure',   // capturing always makes runs slow and output
                              // unreadable; the point of a trace is the
                              // failure nobody watched

A real bug this suite caught in itself

The first full run was 15 UI failures and 9 API passes — every UI test timing out on a missing input. It looked like selector flake.

It was configuration. baseURL was …/todomvc without a trailing slash, and page.goto('/') resolves a leading slash against the origin — so every test loaded demo.playwright.dev/, which returns 404, instead of the application. Both lines now carry a comment explaining why the slash matters.

It is recorded here rather than quietly fixed, because telling those two failure modes apart is most of what this job actually is.
