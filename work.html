Shopify · ecommerce integration Verified · owner-operated store

A catalogue that reported healthy while every product was unbuyable

The problem
A live Shopify store with 51 products showed as fully in stock. The admin dashboard reported the catalogue healthy. The Admin API returned success on every write, with userErrors an empty array. Customers could not buy a single item.
Why it was hard
No individual call was wrong. Connecting a supplier moved inventory to a fulfilment-service location, and that location sat in no delivery profile's location group. Shopify cannot compute a shipping rate for stock it cannot ship from, and a product it cannot ship, it hides. Both facts were correct in isolation; the breakage lived in the combination, which no single endpoint is responsible for reporting. The fulfilment-service location does not even appear in the location group's list unless you explicitly ask for it — so the place the problem lived was invisible in the place you would look.
What was done
Stopped reading the mutation response and wrote a separate query that asks the buyer's question instead of the writer's: for each product, where does the inventory sit, and can any shipping rate reach a customer from there? All 51 failed it. That read now runs against the live store before anything counts as finished, and a real test order is placed before any store is handed over.
Evidence
Reproducible against a live store via the Shopify Admin GraphQL API. The specific trap — locations() omitting fulfilment-service locations unless includeLegacy: true is passed — is the detail that makes the fault invisible, and it is the first thing checked now.
What this does not show
This was our own store, not a client's. The fix is specific to Shopify's delivery-profile model and does not generalise to other platforms.

Developer documentation Verified · published & executable

Documentation where every example was run before the page shipped

The problem
Code samples in documentation rot silently. The page keeps saying what the library used to do, and the reader finds out it is wrong — usually in the middle of trying to use it.
What was done
Every published example is executed against the pinned version before the page ships, and the script that ran it ships alongside. Snippets are extracted from the executed script rather than typed into the prose, so a snippet cannot disagree with the code that produced it. A sample that quietly stops working becomes a failed build instead of a support ticket.
Evidence
Live and readable now: a Zod v4 migration guide, a better-sqlite3 transaction study, pdf-lib, a Playwright suite and a data-cleaning pipeline. The jsonwebtoken writeup corrected advice that turned out to be outdated for v9 — the library already infers the algorithm family from the key type — which was only discovered by testing the claim rather than repeating it.
What this does not show
These are samples written to demonstrate the method, not commissioned client documentation.

Node.js · TypeScript · pinned-version verification · extracted snippets · CI-style sample checks

SaaS · payments · reliability Working prototype · controlled beta

A SaaS assessed honestly, and held back from launch

What it is
A deployed multi-service SaaS with a Paddle webhook receiver, account entitlements and a running production release.
The interesting part
Its own readiness assessment concluded no-go for a paid launch, and named four blockers rather than shipping around them: no checkout had ever actually been completed with a card, there was no password reset so a locked-out customer stays locked out, the legal documents were unreviewed drafts, and the entitlement receiver wrote to a different database from the one serving the site — so a payment could never have reached the customer who made it.
Why it is on this page
Because the fourth blocker is the same shape as the Shopify fault above: every component worked, and the combination did not. Finding that before a customer's money was involved is the capability being offered here, and an assessment that says no is better evidence of it than one that says yes.
What this does not show
It is a controlled beta, not a live paid product. No revenue, no paying customers. The blockers above are open.
