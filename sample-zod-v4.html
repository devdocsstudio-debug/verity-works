Zod v4: Validation Behavior Guide

The five behaviors that surprise people moving to Zod v4 — parse vs safeParse, unknown keys, coercion, optionality, and the order you chain .transform() and .refine().

Sample scope note: this is an independent documentation sample published by DevDocs Studio, the technical-writing service from Verity Works, to show how we work. It is not an official Zod document and was not commissioned by its maintainers. It documents the real, public zod npm package at version 4.6.7 by reading its behavior directly. Every code example and every output shown below was executed against that installed version before publication — no output is assumed, recalled, or illustrative. The verification script is sample-zod-v4-claims-verify.js.

1. .parse() throws; .safeParse() returns

const z = require('zod');

const User = z.object({ name: z.string(), age: z.number().int().positive() });

User.parse({ name: 'Ada', age: 36 });
// -> { name: 'Ada', age: 36 }

User.parse({ name: 'Ada', age: -1 });
// throws ZodError

The thrown ZodError carries an issues array. For the failure above, the single issue is:

{
  origin: 'number',
  code: 'too_small',
  minimum: 0,
  inclusive: false,
  path: [ 'age' ],
  message: 'Too small: expected number to be >0'
}

.safeParse() returns a result object instead of throwing, which is what you want at a request boundary:

const result = User.safeParse({ name: 'Ada', age: -1 });
result.success;        // -> false
result.error.issues;   // -> the same issues array as above

Three error formatters ship in v4, and they produce genuinely different shapes. Given User.safeParse({ name: 123, age: 'x' }):

z.flattenError(result.error);
// -> { formErrors: [], fieldErrors: {
//      name: [ 'Invalid input: expected string, received number' ],
//      age:  [ 'Invalid input: expected number, received string' ] } }

z.treeifyError(result.error);
// -> { errors: [], properties: {
//      name: { errors: [ 'Invalid input: expected string, received number' ] },
//      age:  { errors: [ 'Invalid input: expected number, received string' ] } } }
console.log(z.prettifyError(result.error));
// ✖ Invalid input: expected string, received number
//   → at name
// ✖ Invalid input: expected number, received string
//   → at age

Use flattenError for a flat form-field map, treeifyError when errors can be nested, and prettifyError for logs and CLI output. Reach for the raw issues array when you need the machine-readable code.

2. Unknown keys are stripped by default

z.object({ a: z.string() }).parse({ a: 'x', extra: 1 });
// -> { a: 'x' }          the unknown key is silently dropped

To reject instead, or to keep the extras, use the dedicated constructors:

z.strictObject({ a: z.string() }).parse({ a: 'x', extra: 1 });
// throws ZodError:
// { code: 'unrecognized_keys', keys: [ 'extra' ], path: [], message: 'Unrecognized key: "extra"' }

z.looseObject({ a: z.string() }).parse({ a: 'x', extra: 1 });
// -> { a: 'x', extra: 1 }

Why the default matters more than it looks: stripping is usually right for an HTTP body, but it means a typo in an optional field name fails silently. { notifcations: true } validates cleanly against a schema expecting notifications and the value simply vanishes. If a field being misspelled should be an error rather than a no-op, z.strictObject is the only one of the three that tells you.

3. Coercion follows JavaScript, not your intent

This is the sharpest edge in the library, because z.coerce applies the ordinary JS constructor before validating.

z.coerce.number().parse('42');    // -> 42
z.coerce.number().parse('');      // -> 0        <-- empty string becomes zero
z.coerce.number().parse('abc');   // throws: 'Invalid input: expected number, received NaN'
z.coerce.boolean().parse('false'); // -> true    <-- the STRING "false" is truthy
z.coerce.boolean().parse('');      // -> false

z.coerce.boolean() is Boolean(value). Every non-empty string is truthy, so 'false', '0' and 'no' all coerce to true. For a query parameter like ?active=false this is almost never what the caller meant, and nothing in the schema reports a problem.

When parsing string input where 'false' and '' must be distinguishable from true, map explicitly instead of coercing:

const BoolParam = z.enum(['true', 'false']).transform((s) => s === 'true');

BoolParam.parse('false');  // -> false
BoolParam.parse('maybe');  // throws -- an invalid value is rejected rather than silently becoming true

The same reasoning applies to z.coerce.number() and empty strings: an absent query parameter arriving as '' becomes 0, which passes a .nonnegative() check and looks like a deliberate zero.

4. .optional(), .nullable() and .default() are three different things

const Shape = z.object({
  o: z.string().optional(),
  n: z.string().nullable(),
  d: z.string().default('fallback'),
});

Shape.parse({ n: null });
// -> { n: null, d: 'fallback' }

Two things to read carefully in that output. The optional key o is absent from the result rather than present as undefined, so 'o' in result is false. And d was filled in by its default because the input omitted it.

.nullable() accepts null but not a missing value:

Shape.parse({ n: undefined });
// throws ZodError:
// { expected: 'string', code: 'invalid_type', path: [ 'n' ],
//   message: 'Invalid input: expected string, received undefined' }

So .nullable() is not a relaxation of required-ness. A field that may be either missing or explicitly null needs both, which is what .nullish() expresses.

5. .transform() before .refine() is not the same as after

Both of these look like "trim it and reject blanks". Only one does that.

const A = z.string().transform((s) => s.trim()).refine((s) => s.length > 0, {
  message: 'must not be blank after trimming',
});

A.parse('  hi  ');  // -> 'hi'
A.parse('   ');     // throws: 'must not be blank after trimming'
const B = z.string().refine((s) => s.length > 0, { message: 'must not be blank' })
                    .transform((s) => s.trim());

B.parse('   ');     // -> ''        no error at all

In B, the refinement runs on the original ' ', which has length 3 and passes. The trim happens afterwards, so an empty string is returned as valid data. The check and the normalization are both present and the schema still accepts exactly the input it was written to reject.

The rule: normalize first, then validate the normalized value. Any check whose outcome depends on a transformation has to come after it.

A transformed value is also what you get back from .safeParse(), not the input:

const Num = z.string().transform((s) => Number(s));
const r = Num.safeParse('7');
r.data;         // -> 7
typeof r.data;  // -> 'number'

Why a guide like this, separate from the API reference

The official documentation accurately states that z.coerce.boolean() performs boolean coercion and that .refine() adds a custom check. Both statements are true, and neither tells you that 'false' becomes true, or that putting .refine() before .transform() quietly accepts the input you meant to reject. That gap — between what each method does and what goes wrong the first time someone uses it — is what this kind of documentation is written to close.

Every behavior above was confirmed by running it against zod@4.6.7 on Node v24.21.0 in October 2026. Where a result looks surprising, it is the real observed output, not a simplification.
